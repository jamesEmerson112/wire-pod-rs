Getting started

What you need to know before any call on this page makes sense: which way the traffic runs, how you authenticate, and why behaviour control decides whether a call does anything at all.

Two directions, easily confused

Your robot talks to your server, and your server talks to your robot, over two completely separate surfaces. This page covers only the second one.

DirectionWho dialsEndpointServiceAuth

You to the robotyour server, the app, the Python SDK<robot ip>:443ExternalInterfaceAuthorization: Bearer <client GUID>

The robot never dials ExternalInterface and your server never serves it. Everything in the other thirteen tabs is the second row.

Transport

On WireOS the gateway is not a separate process. It is compiled into vic-cloud and started as a goroutine, listening on TCP 443 with a TLS config whose NextProtos is ["h2"] and nothing else. The same handler serves the gRPC service and a grpc-gateway JSON mux.

The robot's certificate is self-signed and names the robot rather than an IP, so every client in this ecosystem skips verification. There is no working alternative; the certificate chain cannot be validated by anything you have.

The bearer token

Authentication is one check on the HTTP Authorization header, in cloud/cloud/config_linux.go.

  • The header must be present exactly once. Absent gives Unauthenticated "No auth token"; more than one gives "Too many auth tokens".
  • It must start with Bearer . The value compared is authHeader[7:].
  • Basic  is recognised, base64-decoded, and the result thrown away with a // todo. The code then slices at offset 7 anyway, which is one character into the payload because Basic  is six characters. Basic is broken, not merely unsupported.
  • Exactly one path is exempt: /Anki.Vector.external_interface.ExternalInterface/UserAuthentication.

The token you send is the plaintext client GUID. The robot only ever holds hashes of it, in the vic.AppTokens jdoc, cached on disk at /data/vic-gateway/token-hashes.json.

A freshly issued GUID is not accepted at once

The robot refreshes its hash list from jdocs at most once a minute, three times in fifteen minutes and six times an hour, and only when the cache is over an hour old. A token your server has just written into vic.AppTokens can be rejected for up to an hour. UserAuthentication forces a refresh on success, which is the only way to make it immediate.

Behaviour control

Most of the interesting calls only do something while your connection holds behaviour control. You take it by opening BehaviorControl and sending a ControlRequest with a priority.

PriorityValueWhat it actually does
UNKNOWN0Dropped. SDKComponent::HandleProtoMessage assigns the level, then returns early through ANKI_VERIFY. You are never granted control and nothing tells you so. Always set a priority.
OVERRIDE_BEHAVIORS10Activates SDKOverrideAll, which sets disableCliffDetection. This is what wire-pod uses.
DEFAULT20Activates SDKDefault, which leaves cliff detection alone.
RESERVE_CONTROL30Takes the behaviour lock only. You get ControlGrantedResponse immediately, but the handler returns before setting _sdkWantsControl, so the SDK behaviour never activates. Every refusal and every silent drop below still applies. It activates BehaviorSDKLock, whose entire body is one log line, to keep the robot still between scripts.

Three ways a call fails without control

The gateway gates nothing. It forwards everything and the refusal, if any, happens further in. There are three distinct outcomes and only one of them looks like a failure.

  • Seven requests are refused with FORBIDDEN. EnableMarkerDetection, EnableFaceDetection, EnableMotionDetection, EnableMirrorMode, SayText, SetCameraSettings and SetEyeColor. The gateway then overwrites the status for five of them, so you see success. SayText is the only one that reports honestly.
  • Twelve action RPCs are queued and then never answered. Their responses come only from SDKComponent::OnActionCompleted, which runs only while the SDK behaviour is active. The gateway blocks on a channel with no timeout, so your call hangs forever while the robot may still attempt the motion.
  • Four direct motor RPCs are silently ignored. DriveWheels, MoveHead, MoveLift and StopAllMotors land in MovementComponent, whose handlers log a warning and do nothing when _allowExternalMovementCommands is unset. You get REQUEST_PROCESSING and no movement.

What losing control tears down

A higher-priority behaviour takes control back and you get a ControlLostResponse. OnBehaviorDeactivated then, in order: re-arms the seven refusals, disables mirror mode and emits MirrorModeDisabled, removes every vision mode subscription except VisionMode::Viz and emits VisionModesAutoDisabled, restores camera auto-exposure, reapplies all saved settings (which undoes an SDK eye colour), unlocks every animation track, forbids external movement commands again, and restores cliff stopping if this behaviour had disabled it. Image streaming survives on purpose, which is why a camera page works with no control at all.

Releasing it

  • Closing a BehaviorControl stream releases control, because the request handler writes a ControlRelease in a defer.
  • Closing an AssumeBehaviorControl stream does not. That path has no such defer and the SDK behaviour keeps running after you have gone.
  • An explicit ControlRelease clears the connection id before the behaviour deactivates, so the ControlLostResponse that follows carries id 0 and is filtered out. You get no confirmation of your own release. An involuntary loss is delivered correctly.
  • Requesting control wakes a sleeping robot. It is the only SDK message registered as a wake reason, which is the practical fix for the camera hang in the Traps tab.

Action tags

Twelve RPCs carry an id_tag, and the gateway rejects it with InvalidArgument "Invalid Action tag_id" unless it is between 2000001 and 3000000 inclusive. A zero-valued default is rejected, so you cannot leave the field unset. CancelActionByIdTag does not validate the tag it is given.

One answer can go to the wrong caller

The gateway routes engine responses back to waiting RPCs by protobuf message type, not per request. CreateChannel keys listeners on the response type's name and fans each message out to every listener registered for it. Only BehaviorControl and AssumeBehaviorControl also filter on the connection id. Two clients issuing the same call at the same time can receive each other's answers, so serialise per robot.

The REST mirror

Every RPC carrying a google.api.http option is also reachable as JSON on the same port and socket, for example POST https://<robot>:443/v1/update_settings. The marshaller is configured with EmitDefaultValues, UseEnumNumbers, UseProtoNames and, on WireOS, DiscardUnknown. So JSON uses proto field names, enums are numbers, and an unknown key is dropped in silence rather than rejected.

The proto your port vendors

The robot defines ninety RPCs. The copy vendored at crates/wirepod-proto/proto/vector/ has eighty-eight of them; UpdateUserEntitlements and UploadDebugLogs are absent and are marked as such on their tabs. Everything the port knows about exists on the robot.

Comparing field numbers across all the shared files, the messages, behaviour, cube, nav map, response status and alexa protos are identical apart from formatting. Two divergences are real and both are in settings.proto:

  • RobotSettingsConfig is renumbered. The robot has CustomEyeColor custom_eye_color = 3 and every field after it shifts by one, so the vendored default_location at 3 arrives as custom_eye_color, locale at 5 arrives as dist_is_metric, and so on down the message. The RobotSetting enum shifts the same way. A binary UpdateSettings built from the vendored proto sets the wrong settings. JSON over the REST mirror is immune because grpc-gateway matches on field names.
  • The vendored EyeColor enum stops two values short. It ends at CONFUSION_MATRIX_GREEN = 6; the robot also has RAINBOW_EYES = 7 and ROBOT_RED = 8.

UserAuthentication

UserAuthenticationRequestunary
Does
Exchanges a user session token for a client GUID. The gateway proxies to vic-switchboard with AppId: "SDK" and, on success, forces the token hash cache to refresh so the new GUID works immediately.
Parameters
user_session_id and client_name, both bytes. client_name is truncated to 64 characters.
Control
Not needed. This is the one RPC exempt from the bearer check, so it is how you bootstrap with no token at all.

BehaviorControl

BehaviorControlRequestbidi stream
Does
The stream you hold open for as long as you want control. Each request is a oneof of ControlRequest (carrying a priority) or ControlRelease. The robot answers with ControlGrantedResponse, ControlLostResponse, ReservedControlLostResponse or a KeepAlivePing once per second.
Parameters
priority: 10 OVERRIDE_BEHAVIORS, 20 DEFAULT, 30 RESERVE_CONTROL. Zero is UNKNOWN and is dropped.
Control
This is how you get it. It is also the only SDK message that counts as a wake reason, so it wakes a sleeping robot.
Trap
Three, all covered in the Traps tab: priority 0 is dropped in silence, your own ControlRelease is never confirmed because the response is tagged with connection id 0 and filtered out, and RESERVE_CONTROL grants control without activating the behaviour.

BehaviorControlRequestserver stream
Does
The same thing as one ControlRequest on the bidi stream, sent as a single request with a streamed response. Convenient when you never need to release explicitly.
Parameters
Identical to BehaviorControl.
Control
This is how you get it.
Trap
Closing this stream does not release control. Only the bidi handler writes a ControlRelease in a defer. A client that uses this call and then exits leaves the SDK behaviour running on the robot, with cliff detection still off at priority 10.

CancelBehavior

CancelBehaviorRequestunarycontrol
Does
Cancels whatever the SDK behaviour has delegated to, by calling CancelDelegates inside BehaviorSDKInterface. This is how you stop a long behaviour such as LookAroundInPlace early.
Parameters
None.
Without control
The handler lives in HandleWhileActivated, so it is only reachable while the SDK behaviour is active. The gateway returns REQUEST_PROCESSING immediately either way, so you cannot tell from the reply whether anything was cancelled.
Note
The engine does produce a CancelBehaviorResponse carrying OK or FORBIDDEN, but the gateway does not wait for it.

CancelActionByIdTag

CancelActionByIdTagRequestunary
Does
Cancels a queued or running action by the id_tag you gave it. The cancelled action's own RPC then completes with ACTION_RESULT_CANCELLED_WHILE_RUNNING (33554432), if you still have control for the response to be produced at all.
Parameters
id_tag, uint32. Use the tag you sent with the action.
Control
Not needed for the cancel itself to be forwarded.
Trap
Unlike the twelve action RPCs, this one does not run ValidateActionTag, so an out-of-range tag is accepted and simply matches nothing. The gateway returns REQUEST_PROCESSING without waiting, so a cancel that found no such action is indistinguishable from one that worked.

Motion

Four raw motor calls that return instantly and are silently dropped without control, and a set of cancellable actions that block until the motion finishes. Knowing which kind you are calling is the whole game here.

Set a deadline on every call in this tab

The nine action RPCs below block on a channel with no timeout and without consulting your request context. Without behaviour control their response is never produced at all, so the call hangs until your client gives up. The robot imposes nothing.

DriveWheels

DriveWheelsRequestunarycontrol
Does
Sets both tread speeds directly and returns at once. The wheels keep turning until you send another DriveWheels or StopAllMotors; there is no duration and no stop condition.
Parameters
left_wheel_mmps, right_wheel_mmps, left_wheel_mmps2, right_wheel_mmps2, all float. The robot's MAX_WHEEL_SPEED_MMPS is 220 and MAX_SAFE_WHEEL_SPEED_MMPS is 170. Negative drives that tread backwards; opposite signs turn on the spot.
Without control
Silently ignored. It reaches MovementComponent, which logs a warning and returns because _allowExternalMovementCommands is unset.
Trap
You always get REQUEST_PROCESSING, control or not, so a status code tells you nothing. Check the robot.

speed_rad_per_sec, float. Positive raises. The head's mechanical travel is −22° to +45°.
Without control
Silently ignored, same as DriveWheels. You get REQUEST_PROCESSING and the head does not move.

Cube handling

Seven manipulation actions. All of them need the cube to be a known object in the robot's world, which means marker detection has seen it or the cube is connected and being tracked. Six take an id_tag; one is a behaviour and does not.

Getting an object id

Every call here except RollBlock takes an object_id. A negative value means "the currently selected object", which is the robot's own choice. Positive ids come from the object_event stream, specifically RobotObservedObject.object_id, or from ConnectCubeResponse.object_id. Marker detection must be on for the first of those, and marker detection needs behaviour control.

Speech and audio

Four calls. One speaks, one sets the volume, one plays your audio through the speaker, and one that looks like a microphone feed is not one.

SayText

SayTextRequestunarycontrol
Does
Speaks the text through the robot's text-to-speech and blocks until the utterance finishes. The gateway loops on the response channel until state reaches FINISHED (4), passing through GENERATING (1), READY (2) and PLAYING (3).
Parameters
text string; use_vector_voice bool, false giving a plain synthesised voice instead of the processed Vector one; duration_scalar float from 0.05 (fast) to 20.0 (slow); pitch_scalar float from −1.0 (low) to +1.0 (high).
Without control
Refused with FORBIDDEN, and this is the one refusal you can actually see. The engine's refusal leaves state at the zero value INVALID, and the gateway maps that to gRPC Internal with the message "Failed to say text".
Trap
Because it blocks until the utterance ends, a long string holds the RPC open for as long as it takes to say it, and there is no gateway timeout. Set a client deadline that accounts for duration_scalar.

SetMasterVolume

MasterVolumeRequestunary
Does
Writes the speaker volume through SettingsManager, so it persists in vic.RobotSettings and survives a reboot. This is a settings write, not a session override.
Parameters
volume_level, a MasterVolumeLevel: VOLUME_LOW (0), VOLUME_MEDIUM_LOW (1), VOLUME_MEDIUM (2), VOLUME_MEDIUM_HIGH (3), VOLUME_HIGH (4).
Control
Not needed. The engine case has no behaviour check.
Trap
You cannot mute. The engine adds one to your value before writing it, because the settings Volume enum has MUTE at 0 and this RPC deliberately skips it. A value above 4 is rejected with FORBIDDEN and nothing is written, but the gateway overwrites the status to RESPONSE_RECEIVED, so an out-of-range volume reads as success. Read back with PullJdocs if it matters.

AudioFeed

AudioFeedRequestserver stream
Does
Not what the name says. On this firmware it streams a synthesised 1 kHz sine wave, not microphone audio. The only producer of external_interface::AudioChunk in the engine is SDKComponent::UpdateDependent, whose comment calls itself a "temporary 1 kHz sine wave generator to test over the wire transfer", with a TODO to replace it with a subscription to the real feed.
Parameters
None.
Control
Not needed. Opening the stream sets the robot's audio mode to AUDIO_VOICE_DETECT_MODE and a defer sets it back to AUDIO_OFF when you disconnect.
What arrives
One AudioFeedResponse per 100 ms, reassembled from ten engine chunks of 160 samples into signal_power of 1600 samples, which is 3200 bytes of 16-bit signed PCM. The wave is sin(πi/8) at amplitude 1000 rather than full scale, so it cycles every 16 samples against the 16 kHz processing rate.
Trap
The metadata is hard-coded, so none of it means anything: direction_strengths is twelve zero bytes, source_confidence is 0, noise_floor_power is 0, and source_direction is 12, which the proto itself documents as the invalid value. The transport is completely correct, frames arrive on time, and nothing reports an error. There is also no RPC for AudioSendMode: the message exists and the engine consumes it, but no method on the service takes it, and the engine's handler only sets a boolean, so the three processing modes are indistinguishable from outside.

ExternalAudioStreamPlayback

ExternalAudioStreamRequestbidi stream
Does
Plays your PCM through the robot's speaker. Fully implemented, unlike AudioFeed: the requests reach the animation process and the robot really makes the sound.
Parameters
Each request is a oneof of four. ExternalAudioStreamPrepare carries audio_frame_rate uint32 from 8000 to 16025 and audio_volume uint32 from 0 to 100. ExternalAudioStreamChunk carries audio_chunk_size_bytes and audio_chunk_samples, 16-bit little-endian PCM, with a current engine maximum of 1024 bytes per chunk. ExternalAudioStreamComplete and ExternalAudioStreamCancel are empty.
Control
Not needed. The four engine cases have no behaviour check.
What comes back
A oneof of ExternalAudioStreamPlaybackComplete, ExternalAudioStreamBufferOverrun (carrying audio_samples_sent and audio_samples_played, which is how you find your pacing) and a playback failure.
Trap
The failure field is misspelled in the proto as audio_stream_playback_failyer, so generated accessors carry the typo and so must your code. A request with none of the four oneof arms set is rejected with InvalidArgument and, because the rejection happens in the request-handling goroutine, it closes the stream rather than answering.

Animation and face

Playing the robot's canned animations, listing the ones it knows, and taking over the screen yourself.

PlayAnimation

PlayAnimationRequestunarycontrol
Does
Plays one named animation and blocks until it finishes. The reply echoes back the animation the robot actually executed.
Parameters
animation, an Animation message whose only field is name; loops uint32; ignore_body_track, ignore_head_track, ignore_lift_track, all bool, which let the animation play without moving that part.
Without control
The PlayAnimationResponse is produced only by SDKComponent::OnActionCompleted, which runs only while the SDK behaviour is active, so the call hangs. Whether the request itself is refused on the CLAD path is unconfirmed.
Trap
loops of 0 and 1 are not obviously different, and neither is documented. There is no gateway timeout on this call, so a long or looping animation holds the RPC open for its whole duration.

PlayAnimationTrigger

PlayAnimationTriggerRequestunarycontrol
Does
Names a trigger rather than an animation and lets the robot pick a variant from that group, which is what makes repeated behaviour look less mechanical.
Parameters
animation_trigger, an AnimationTrigger whose only field is name; loops; use_lift_safe bool, which drops the lift track automatically if the robot is carrying something; and the same three ignore_*_track flags.

Same as PlayAnimation: no response is produced and the call hangs.
Trap
It returns a PlayAnimationResponse, not a trigger-specific message, and the gateway says why in a comment: in the end the engine is playing an animation. Because responses are matched by type, a concurrent PlayAnimation on another connection can collect this one's reply.

Camera and vision

Image streaming is deliberately ungated and works with no control at all. Every other vision mode is refused without control, and every one of them blocks the gateway with no timeout until the vision system confirms the change.

The single most expensive behaviour on the robot

The engine does not answer a vision toggle immediately. It adds the mode to a pending list and only replies once a processed camera frame shows the mode has actually appeared or disappeared. A sleeping robot has paused its vision component and may have deleted the camera outright, so no frame is produced and the confirmation never comes. The gateway blocks on that channel with no timeout and without reading your request context, so your call hangs.

The fix is on your side: take behaviour control first. Requesting control is the only SDK message registered as a wake reason, so the robot wakes and the camera calls then answer.

Traps

The behaviours that cost a day. Each one is something the robot does that no status code, log line or error will tell you about.

Silence and hangs

A sleeping robot never answers a camera call

EnableImageStreaming blocks on a channel with no timeout and without consulting your request context. The engine does not reply until a processed camera frame confirms the mode changed, and a sleeping robot has paused its vision component and may have deleted the camera, so the confirmation never comes. CameraFeed and CaptureSingleImage both start by calling it, so they hang too, and their deferred disable waits on the same confirmation, so teardown can block as well. Take behaviour control first: requesting control is the only SDK message that counts as a wake reason.

Every action RPC hangs without behaviour control, and always will

The twelve action calls are queued on the robot regardless of control, but their responses are produced only by SDKComponent::OnActionCompleted, which runs only while the SDK behaviour is active. So the motion may be attempted and the reply never comes. Set a deadline on every call.

A ControlRequest with no priority is dropped in silence

Priority zero is UNKNOWN and the engine returns early through ANKI_VERIFY before setting anything. The stream stays open, the keep-alives keep arriving, and you are simply never granted control.

RESERVE_CONTROL grants control that is not control

Priority 30 takes the behaviour lock and returns before _sdkWantsControl is set, so you receive ControlGrantedResponse but the SDK behaviour never activates. All seven refusals stay armed, the motor commands stay dropped, and no action response is ever produced. It exists to keep the robot still between scripts, not to run them.

AssumeBehaviorControl does not release when the stream closes

Only the bidirectional BehaviorControl handler writes a ControlRelease in a defer. Use the simpler call and exit, and you leave the SDK behaviour running, with cliff detection still disabled if you asked for priority 10.

You are never told your own release succeeded

An explicit ControlRelease clears the connection id before the behaviour deactivates, so the ControlLostResponse that follows carries id 0 and the response handler filters it out. An involuntary loss is delivered correctly, so the absence of a message does not mean the absence of a change.

Success that is not success

Refusals are usually invisible

Of the seven requests the engine refuses with FORBIDDEN when you lack control, five have their status overwritten by the gateway to RESPONSE_RECEIVED: the four vision toggles and SetCameraSettings. SetEyeColor is worse, because the gateway registers no listener for its response at all and returns REQUEST_PROCESSING immediately, so the refusal goes to nobody. SayText is the only one that reports honestly, and only by accident: the refusal leaves state at the invalid zero value and the gateway maps that to Internal "Failed to say text".

The single useful exception is SetCameraSettings, whose status_message is left untouched by the rewrite. A non-empty message on a RESPONSE_RECEIVED reply means the call was rejected, and the text names the permitted ranges.

The four motor calls return success and do nothing

DriveWheels, MoveHead, MoveLift and StopAllMotors reach MovementComponent, whose handlers log a warning and return when _allowExternalMovementCommands is unset. Nothing is sent back. You get REQUEST_PROCESSING either way. Do not infer that a call worked from its status code; check the robot.

An out-of-range volume reads as success

SetMasterVolume above level 4 is refused by the engine with FORBIDDEN and nothing is written, but the gateway overwrites the status to RESPONSE_RECEIVED. The engine also adds one to your value on the way in, because it deliberately skips MUTE, so you cannot mute the robot through this call at all.

Six calls confirm nothing at all

CancelFaceEnrollment, UpdateEnrolledFaceByID, EraseEnrolledFaceByID, EraseAllEnrolledFaces, DisconnectCube and SetCubeLights are written and answered with REQUEST_PROCESSING before the engine has seen them. Three of the face calls carry a TODO in the gateway saying they should wait for a confirmation and do not. Watch the corresponding event instead.

A rate-limited CheckCloudConnection returns a stale answer

Beyond one call per ten seconds or three per minute, the handler returns the previous result rather than an error, because a TODO records that the ResourceExhausted error was removed for the app's benefit. A polling loop will happily show you a connection state from several minutes ago.

Wire format and shape

Settings sent as binary protobuf land on the wrong fields

The robot's RobotSettingsConfig has custom_eye_color at field 3, which the vendored copy lacks, so everything from field 3 down shifts by one on the wire. Use the JSON REST mirror for settings, where grpc-gateway matches on field names. The vendored EyeColor enum is also two values short, missing RAINBOW_EYES (7) and ROBOT_RED (8).

The REST surface ignores unknown JSON keys

DiscardUnknown is on, so a typo in a settings key is silently a no-op rather than an error. A test that asserts a 400 on a bad field will never pass.

The face image is not RGB565 and not little-endian

Three things have to be right at once for DisplayFaceImageRGB. The buffer must be exactly 17,664 pixels at two bytes each, which is 35,328 bytes, because the gateway slices by computed offsets with a TODO admitting it will "implode on empty". The packing is 000bbbbbrrrrrggg, five bits of blue, five of red and three of green, so a wrong guess swaps channels rather than failing. And the byte order is contested: the robot's gateway reads each pixel with binary.BigEndian.Uint16 while wire-pod writes its computed uint16 little-endian, so the two disagree by a swap and only a test on the robot settles it.

NavMapFeed frequency is seconds, not hertz

The gateway logs it as seconds and sends the CLAD message SetMemoryMapBroadcastFrequency_sec. Asking for 30 gets you one map every thirty seconds.

SetCubeLights needs exactly four of everything, and a non-zero mode

The engine copies each repeated field into a fixed four-element array with no length check. It also rejects make_relative of 0 outright, logging "Got relative mode 0 (Unknown) from gateway, ignoring call" and dropping the request. Since 0 is the proto default, an unset field means nothing happens and nothing is reported.

id_tag must be in a narrow range, and zero is outside it

The twelve action RPCs reject any tag outside 2000001 to 3000000 with InvalidArgument "Invalid Action tag_id", so leaving the field at its default fails. CancelActionByIdTag does not validate the tag at all, so an out-of-range cancel is accepted and matches nothing.

The surface itself

Engine responses are matched by message type, not by request

CreateChannel keys listeners on the response type's name and fans each message out to every listener registered for it. Only BehaviorControl and AssumeBehaviorControl filter on the connection id as well. Two clients making the same call against one robot can receive each other's answers. Serialise per robot.

AudioFeed returns a test tone

The only producer of external_interface::AudioChunk in the engine synthesises a 1 kHz sine wave at amplitude 1000, with a comment saying so and a TODO to replace it. The metadata is hard-coded: twelve zero bytes of direction strength, zero confidence, zero noise floor, and source_direction of 12, which the proto documents as the invalid value. The transport is entirely correct, frames arrive on schedule, and nothing reports an error.

Several calls do less than their names promise

  • CaptureSingleImage never reaches the engine; its subscription there is a commented-out line.
  • CameraFeed ignores high resolution by design, with a comment saying the video stream uses only the default.
  • SetPreferredCube carries a proto comment saying it is only used in simulation for now.
  • UploadDebugLogs has its upload body commented out on this firmware and returns OK with an empty URL.
  • AudioSendMode has no RPC at all. The messages exist and the engine consumes the request, but nothing on the service takes them and the handler only flips a boolean.
  • RobotStatusHistory has a handler in the gateway but no rpc entry in the service, with a comment explaining that a hundred-entry result is too large for the domain socket to the engine. No client can reach it.
  • ProtocolVersion checks nothing, because the minimum version is 0.

Basic authorization is broken, not merely unsupported

The gateway accepts the Basic  prefix, base64-decodes the value, throws the result away with a // todo, and then slices the header at offset 7 anyway, which is one character into the payload because Basic  is six characters long. Use Bearer.

A newly written token is not accepted immediately

The robot caches the vic.AppTokens hash list at /data/vic-gateway/token-hashes.json and refreshes it at most once a minute, three times in fifteen minutes and six times an hour, and only when the cache is over an hour old. A GUID your server has just written can be rejected for a long time. UserAuthentication forces a refresh on success, which is the only way to make one live at once.

The animation lists are filtered and deadlined, differently from each other

ListAnimations drops every name containing _avs_ and times out after five seconds with DeadlineExceeded and no partial list. ListAnimationTriggers lowercases each name and drops any containing deprecated or alexa, and its deadline is ten seconds. The sentinel EndOfListAnimationsResponses exists on the engine-to-gateway path only; the gateway consumes it and you never see it.

A concurrent settings write is refused, not queued

UpdateSettings, UpdateAccountSettings and UpdateUserEntitlements each take a unique channel. A second call while one is in flight returns at once with status ERROR_UPDATE_IN_PROGRESS (102) and writes nothing.
